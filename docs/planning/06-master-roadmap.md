## 2. Decisions revised mid-review (so the history isn't lost)

Planning is not a one-pass process — these changed after the first draft, based on review:
- **Media file cleanup**: `02` §1 originally proposed an `EventBus`-fan-out delete handler; revised in `03` §3 to a direct transactional call through a cross-module port, because a single listener doesn't need event indirection and a transaction guarantees no orphan window.
- **Frontend API exposure**: `01` §4 originally reserved `NEXT_PUBLIC_API_BASE_URL` for direct browser calls; dropped in `04` §3/§10 once every browser-originated call turned out to be proxyable through a Route Handler — only `INTERNAL_API_BASE_URL` remains.
- **Backend build order**: `03` §1 was reordered after review — Technology moved ahead of Contact (it's a real dependency of Case), and Case/Post were pulled forward ahead of Contact specifically to reach the highest-risk part of the architecture early rather than last.
- **Admin session check**: `04` §4 originally planned local JWT verification (`jose` + a secret shared between Next and the backend); revised to calling the backend's existing `GET /auth/me` per request, trading a negligible internal-network latency cost for keeping the backend as the single source of truth on session validity.
- **Refresh-token race**: confirmed as a real risk (not theoretical) against the actual `refresh-tokens.handler.ts` rotation/theft-detection logic — `04` §4 adds an in-memory single-flight guard, with an explicit note on why it's safe *now* (single Node process) and what changes if that ever isn't true (move the lock to Redis).

## 2.5. Decisions and fixes discovered during implementation (not caught in review)

Planning review (§2) caught what it could reason about ahead of time; these surfaced only once real code, a real database, and a real container restart were in the loop. Recorded here so they aren't silently lost and so the same mistakes aren't repeated in future modules:

- **CASL `role_permission` seeding is a required step per module, not implied by `@Policy(...)`.** `03` §2's module template said to wire `@Policy(...)` against a `Subjects` value already added to the enum — but the CASL ability actually granted to a role is driven entirely by rows in `migration/configs/roles.config.ts`, seeded separately. Every Phase 2 module (Hero/About/SiteSetting/Contact/Technology/Navigation/Case/Post/Comment) shipped with its `@Policy` decorators correctly in place but **zero corresponding `role_permission` entries** — meaning the entire admin CRUD surface returned 403 for every one of these modules from the moment each was built. This went undetected through all of Phase 2/3 because testing focused on public endpoints; it surfaced only in Phase 4 when the admin screens actually tried to call these endpoints with a real token. Fixed by adding the full permission set for all nine modules in one pass. **`03` §2's module template now includes this as an explicit step** (see the updated template) — add the `role_permission` entries in the *same commit* as the `@Policy` decorators, not after.
- **View-count increment endpoints were missing from the original endpoint matrix.** `02` §9 described the Redis-dedup mechanism conceptually, but neither `03`'s per-module notes nor `02` §10's CASL matrix ever actually specified a `POST /cases/:slug/view` / `POST /posts/:slug/view` endpoint — the DTOs carried `viewCount` from day one, but nothing ever incremented it. Added retroactively in Phase 3: a shared `ViewTrackingModule` (Redis `SET NX` dedup, 30 min window, keyed by a hash of IP+UA) plus one endpoint per entity, reusing the same repository/command/handler pattern as everything else.
- **The public comment/captcha flow had no working captcha until Phase 4.** `02` §7 correctly identified that `COMMENT_SUBMIT` needed adding to `CaptchaChallengeContext`, but nothing in `02`/`03` flagged that the captcha subsystem also needs a seeded default template + active config + a populated Redis asset pool before *any* challenge can be created — without one, every challenge request 404s with `captcha.template.notFound`. Fixed with a new `CaptchaTemplateSeedService` (seeds a default `svg-text-ru-v1` template + config on first boot, mirroring the Hero/About/SiteSetting seed pattern) plus a `CaptchaPoolReplenishmentService` (`@Cron`, tops up any template/difficulty pool that drops below a watermark) — without the latter, the pool would have silently drained to zero again after enough real submissions, exactly as it did during testing.
- **NestJS CQRS bootstrap-order gotcha**, hit while building the pool-replenishment service above: `CommandBus`/`QueryBus` handlers are registered by `CqrsModule` during `onApplicationBootstrap`, which runs *after* every module's `onModuleInit`. A service that calls `commandBus.execute(...)` from `onModuleInit` throws `CommandHandlerNotFoundException` — crashed the backend container at boot the first time. Fixed by using `OnApplicationBootstrap` instead. Not something `03`'s module template could have anticipated (none of the Phase 2 modules touch the bus at boot time); worth remembering for any future boot-time hook that does.
- **The reorder endpoint (`05` §2's addendum) was originally N sequential `UPDATE`s in one transaction**, not the single bulk statement the addendum's own rationale calls for ("chattier than necessary... not atomic"). Caught in code review (not by any test) across all four orderable collections (Case/Contact/Technology/Navigation); fixed to one `UPDATE ... FROM (VALUES ...)` statement per reorder call — one round trip regardless of item count, transaction no longer needed since it's a single statement.
- **A stale `create-next-app` default `app/layout.tsx`** (from the original scaffold, never deleted) was silently winning as the actual Next.js root layout for the entire public site — `lang="en"`, no theme provider, no Cyrillic font subset were ever actually being applied, undetected until an HTML response was inspected directly. Fixed by deleting it; `app/[locale]/layout.tsx` is the sole root layout (Next.js supports this without a top-level `app/layout.tsx` when every route lives under a segment that has its own).
- **Fonts**: `04` §9 deliberately left exact type choices as an implementation-time decision. Settled on self-hosted variable fonts — **Unbounded** (display/headings), **Onest** (body), **JetBrains Mono** (mono/labels) — downloaded once from their source repos (not `next/font/google`, which still fetches from Google at build time even though it self-hosts the *served* files) and committed under `apps/frontend/src/fonts/`, loaded via `next/font/local`. Chosen by generating a self-contained HTML preview artifact with the real candidate files embedded as base64, rather than picking from names alone. Along the way, found and fixed a pre-existing bug in `globals.css`: `--font-sans: var(--font-sans)` was a circular self-reference (should have pointed at the actual font variable), meaning the previous font was never rendering as intended either.
- **Mobile responsiveness was never called out as its own line item in any phase below** — it surfaced as a dedicated request after Phase 4 shipped, not from re-reading `04`/`05`. Real, non-cosmetic issues found: the public header's nav was `hidden sm:flex` with **no mobile alternative at all** (phones had no way to reach Cases/Posts/About), and the admin shell's sidebar was a fixed 220px flex sibling with no mobile fallback (would have crushed admin content into a sliver on any phone). Both fixed — a hamburger-menu overlay for the public header, and a top-bar-plus-drawer pattern for admin below `lg` (chosen over `sm` for admin specifically because the nav has ten items with long labels, needing more room before the sidebar layout makes sense). See the new `04` §14.
- **CQRS commands/queries across every content module were never typed against `@nestjs/cqrs`'s `Command<TResult>`/`Query<TResult>` base classes**, unlike the pre-existing `users`/`file` template modules (e.g. `UserGetByIdQuery extends Query<UserDto>`). Every command/query class built in Phases 2–4 (Hero, About, SiteSetting, Technology, Navigation, Contact, Case, Post, Comment, plus the Captcha module) was a bare class with no base type, forcing every call site to either pass explicit `commandBus.execute<TCommand, TResult>(...)` / `queryBus.execute<TQuery, TResult>(...)` generics (easy to get wrong or forget) or silently fall back to `any`. Caught in code review, not by any test or lint rule — TypeScript happily compiled the untyped version since `CommandBus.execute`/`QueryBus.execute` default their result generic to `any`. Fixed across all ten modules: every command/query now `extends Command<T>`/`extends Query<T>` with `T` matching what its handler actually returns, and every call site simplified to the inferred `execute(new XCommand(...))` form. Handlers themselves didn't need to change (`implements ICommandHandler<X>`/`IQueryHandler<X>` already worked regardless). **Worth adding as an explicit step to `03` §2's module template**, alongside the `role_permission` seeding step from the first finding above — this is exactly the kind of gap that's invisible until someone reads a diff side-by-side with the reference module.
- **`TranslationTabs`' hidden-panel + native `required` combination silently blocks form submission**, and looked exactly like a dead button with no console error visible to a normal user. The inactive locale panel is hidden via Tailwind's `hidden` (`display:none`) so switching tabs never drops unsaved state (`05` §1) — but several forms (Hero, About, SiteSettings, Case, and the original bilingual Post editor) also put native `required` attributes on fields inside those panels. Submitting with the other tab's required fields still empty (the default state for anything brand-new) makes the browser try to focus an un-focusable field and throw `An invalid form control with name='' is not focusable`, which blocks the submit entirely — caught only because the user reported the "Create" button doing nothing and a browser console screenshot showed the actual error, not from any test (jsdom doesn't reproduce this native-validation-vs-`display:none` interaction). Fixed by adding `noValidate` to every affected `<form>` plus explicit manual validation in each `handleSubmit`, across all five forms. Directly motivated the Post schema change below, since one root cause of the bug for Post specifically was that it never should have had two required locale panels in the first place.
- **Post was de-bilingualized mid-session** (not a planning revision, a real product correction) — see the new Phase 4.8 and `02-content-model.md` §7. `post_translation` is gone; `post` carries `locale`/`title`/`slug`/`excerpt`/`body`/`seoTitle`/`seoDescription` directly, one row per post, `locale` fixed at creation. Comment's `resolvePublishedPostId` (which joined through `post_translation` to resolve a post by locale+slug) was updated to query `post` directly. The generated migration failed on the first attempt against leftover soft-deleted debug posts from testing the bug above (`ADD COLUMN ... NOT NULL` needs a default or an empty table) — a reminder that soft-deleted rows still count as real rows to a schema migration.
- **`FileDto` never exposed `type` (IMAGE/VIDEO/DOCUMENT/OTHER/USER_FILE)**, discovered while building `FileUploadField`/`MediaGalleryField` (Phase 4.7) — a different, older gap than the `position`/`isCover` fields added in Phase 1 (those were on the DTO from the start, just unused until now). About needs both a photo and a résumé attached to the same entity, disambiguated only by `type` (`02-content-model.md` §3) — impossible to build against without it. Fixed by adding `type` to `FileDto`/`FileMapper` alongside the admin controller work.
- **A real photo upload hung forever — first real bug report from actual use, not from a planning gap.** Traced through three wrong hypotheses before finding it: not Next.js Server Actions' 1MB body limit (raised it anyway, harmless but not the cause), not a Server-Action-vs-Route-Handler issue (switched `FileUploadField`/`MediaGalleryField` to a plain `fetch()` → `app/api/admin/files/route.ts` Route Handler anyway, since it matches the codebase's existing proxy pattern for captcha/comments/view and is one less moving part — but the hang reproduced identically hitting the backend directly with curl, proving the frontend was never the problem). **Actual cause:** `FileAdminController.parseAdminUpload` stored the multipart file part in a variable and called `.toBuffer()` on it only *after* the `for await (const part of multipartRequest.parts())` loop finished — but `@fastify/multipart`'s iterator can't advance past a file part until its stream is drained, so the loop (and the whole request) hung forever for any file too large to fit in the stream's internal buffer by accident (a ~70-byte test file during earlier smoke-testing happened to fit, masking the bug completely). The pre-existing reference implementation, `FileController.parseCurrentUserUploads`, already calls `.toBuffer()` immediately upon encountering the file part, inside the loop — exactly the pattern that should have been copied the first time. Fixed by draining the buffer at the point of encounter, matching the reference. Verified with real multi-megabyte uploads (2–3MB) through curl directly against the backend and through the full browser→Route Handler→backend chain — both now complete instantly.
- **Re-uploading to a single-file slot after deleting it left the file permanently invisible, even though the re-upload itself reported success.** `FileRepositoryDrizzle.uploads()`'s `onConflictDoUpdate` (the mechanism that makes replacing a Hero/About/SiteSettings/Post cover work in place, per the `(name, module, externalId)` unique constraint) updates `description`/`type`/`position`/`isCover`/`updatedAt` on conflict but never cleared `deletedAt` — so delete-then-reupload to the same slot resurrected the row's content but left its old soft-delete timestamp in place, making every read filter (`WHERE deletedAt IS NULL`) exclude it forever. Found while smoke-testing the multipart fix above, on a slot that had genuinely been deleted-then-reuploaded earlier in the same debugging session. Fixed by adding `deletedAt: null` to the conflict `set` clause.
- **Public pages never rendered any of the images uploaded via Phase 4.7's `FileUploadField`/`MediaGalleryField`** — the widgets were built and verified against the *admin* panel, but nothing on the actual public site (Hero avatar, About photo, Case/Post cover thumbnails, Case/Post detail cover, markdown body images) ever fetched or displayed them, since public entity DTOs don't embed file references (the `(module, externalId)` association is intentionally separate — `02-content-model.md` §1). Closed with one new addition: a public, unauthenticated `GET /file/external/:externalId` endpoint (hardcoded to `FileFrom.PUBLIC` only, so it can never enumerate another user's private uploads) plus `entities/file/api.ts`/`covers-by-id.ts` on the frontend, wired into the homepage, About/Cases/Posts list pages, and Case/Post detail pages. Markdown body images (`![alt](/api/files/<id>)`) needed no new work — `MarkdownContent`'s existing `img` renderer and the already-public `/api/files/[id]` proxy handled it as-is once confirmed with a real published post.

### Phase 4.6 — Draft Mode preview ✅ done (the first of `05` §6's two deferred items, picked back up)
Built exactly as designed in `05` §3: backend `Case/PostGetBySlugAnyStatusQuery` + `findBySlug` repository method + `GET /admin/{cases,posts}/preview/:slug` controller endpoints; frontend `app/api/preview/route.ts` (admin-auth check via `GET /auth/me`, then `draftMode().enable()` + redirect to the real public URL) and `app/api/preview/disable/route.ts` (`draftMode().disable()`); the public Case/Post detail pages branch on `draftMode().isEnabled` to call the admin-auth'd any-status fetch instead of the public published-only one; `widgets/exit-preview-banner.tsx` replaces the view-count beacon while previewing (a draft view must never count); "Preview RU"/"Preview EN" links added next to `StatusControl` in both admin editors.

**Definition of done:** a `DRAFT` case/post renders correctly (same components as the real published page) for an admin who followed a Preview link, shows the exit-preview banner, and stops rendering (reverts to the public 404) once "Exit preview" is clicked — while an ordinary visitor with no admin session gets a 404 on that same slug throughout, on both the page route and the raw public API. **Verified via curl smoke test against the running docker stack** (login → create a throwaway DRAFT case → hit `/api/preview` → confirm 200 + banner → confirm public 404 for the same slug with no cookies → hit `/api/preview/disable` → confirm the same admin now also gets 404 → deleted the throwaway case), not just a code read.

### Phase 4.7 — FileUploadField/MediaGalleryField ✅ done (the second of `05` §6's two deferred items, picked back up)
Built as designed in `05` §1: `FileUploadField` (single-slot: Hero/About photo, About résumé, Site Settings favicon, Post cover) and `MediaGalleryField` (Case cover + ordered gallery). Backend additions: `File` entity/DTO/mapper gained `type` (previously never exposed at all — a gap distinct from `position`/`isCover`, which were added in Phase 1 but likewise unused until now), a new `FileAdminController` (`GET/POST /admin/files`, `PATCH /admin/files/reorder`, `PATCH /admin/files/:id/cover`, `DELETE /admin/files/:id`) gated on the pre-existing `Subjects.FILE_ADMIN` (already seeded for Administrator — the first new admin surface this project added that *didn't* need a `roles.config.ts` change, unlike the §2.5 finding below about every other module), and `deleteByExternalId` wired into Case/Post's delete handlers so removing an entity also removes its files (skipping the `FileAssociationCleanerPort` `02-content-model.md` §1 designed for this, in favor of injecting the already-`@Global()` `FileRepository` directly — the port pattern earns its keep across a real module boundary like `auth-service`'s gRPC split, not within one Nest app). Frontend: `app/api/files/[id]/route.ts` proxies file bytes the same way `app/api/captcha/image/[id]/route.ts` already did, keeping the "browser never calls the backend directly" rule intact for `<img>` tags.

**Definition of done:** an admin can upload, replace, and remove a cover image on Hero/About/SiteSettings/Post, upload a résumé on About, and manage a reordered gallery with a chosen cover on Case — verified via curl smoke test against the running docker stack (upload → confirm it appears via `GET /admin/files` → confirm the public proxy serves it unauthenticated → delete → confirm gone), not just a code read.

### Phase 4.8 — Post de-bilingualized: one post, one language ✅ done (real-world correction, not originally planned)
Caught mid-session, after Phase 4's Post editor had already shipped with the same `TranslationTabs` RU+EN pattern as Hero/About/SiteSettings/Case: a blog post isn't bilingual content the way those four are — forcing every article into a dual-language pair doesn't match how a single-author blog actually gets written, and it was the direct cause of the `TranslationTabs` bug above (an admin filling in only the language they're writing in left the *other* locale's hidden `required` fields empty, which is exactly the state that broke submission). Fixed at the schema level, not just the UI: `post_translation` dropped entirely, its columns merged onto `post` directly behind a single `locale` column fixed at creation (see `02-content-model.md` §7). Public reads filter by `locale` — a post written in `en` simply doesn't exist when browsing the `ru` site, no cross-locale fallback. `PostDto.alternates` (sibling-locale slugs, for hreflang) was removed along with the concept it served.

**Migration note:** the generated migration (`0012_post_single_locale.sql`) added `NOT NULL` columns to `post` and failed against a handful of soft-deleted debug rows left over from testing the `TranslationTabs` bug above (`ADD COLUMN ... NOT NULL` can't backfill existing rows with no default) — caught immediately since this environment had zero real posts, cleaned up by hard-deleting those specific leftover rows before re-running. Worth remembering for any future migration that adds a `NOT NULL` column: soft-deleted rows are still real rows as far as `ALTER TABLE` is concerned.

**Definition of done:** creating a post requires picking exactly one language; a `ru`-locale post appears in `GET /posts?locale=ru` and its own page, and 404s on both the API and the public page under `/en/`; the admin editor is one flat form (no tabs) with the language fixed after creation. **Verified via curl + live frontend smoke test** against the running docker stack (created a `ru` post, published it, confirmed it appears in the `ru` list/detail and is entirely absent from `en`, confirmed the same through the actual Next.js dev server, not just the raw API).

### Phase 5 — Hardening & go-live (in progress)
- Full stack smoke test from fresh volumes (migrations run, admin bootstrap, real content seeded — not fixtures). **Done** — `docker compose down -v && up -d` from empty Postgres/Redis/MinIO volumes: all 12 migrations + every seed service (roles/permissions, admin user, Hero/About/SiteSettings placeholders, captcha template, notification/email templates) ran cleanly; admin login, public pages, and a captcha challenge all worked immediately after boot with no manual intervention.
- Security pass: production config (`config.production.yaml.example`-derived) has every required secret set; `throttle` limits reviewed for public endpoints, especially comment submission; confirm whether backend is deliberately kept off the public internet (`01` §4's option, now genuinely available since the browser never calls it directly). **Done** — found and fixed a real gap: `POST /captcha/challenges`, `POST /captcha/:id/verify`, and `POST /posts/:slug/comments` had no route-level `@Throttle`, falling back to the global 100/min default. For captcha specifically this was a genuine DoS vector — the Redis asset pool only refills every 5 minutes (`CaptchaPoolReplenishmentService`), so an unthrottled attacker could drain it faster than it refills and 503 every real visitor with `captcha.pool.empty`. Added `@Throttle({ ttl: 60_000, limit: 20 })` to both captcha routes and `limit: 5` to comment submission, matching the existing pattern on `/auth/login`.
- **New finding, not in the original Phase 5 scope: the frontend Docker image could not be built at all.** `docker compose build frontend` failed — the home/about/cases-list/posts-list pages fetch backend data with `next: { revalidate, tags }` (`04` §5's intended on-demand-revalidation design), which makes Next.js attempt to statically prerender them *during `next build`*, but the isolated Docker build stage has no network path to any backend (compose networking only applies at `up`, not `build`). This had apparently been broken since these pages were first built in Phase 3 — local development never caught it because `next dev`/`next build` run directly on the host, which *can* reach the docker-exposed backend port. **Fixed** by adding `export const dynamic = "force-dynamic"` to all four affected pages — they now render per-request instead of at build time, while the fetch-level Data Cache (`revalidate`/`revalidateTag`) still applies, so the on-demand revalidation design from `04` §5 is unaffected. Also added `.env.local` to `.dockerignore`, since a dev-only file pointing at the docker-exposed host port had been silently entering the build context. Verified: `docker compose build frontend` now succeeds with zero network access, and the resulting container serves the real site (confirmed against freshly-seeded placeholder content, not cached/stale HTML).
- Real coverage check against the existing 85% line/branch threshold (`00-audit.md` §8). **Done — real number is 21.88% statements / 12.55% branches**, far below threshold. This is not a regression from this session's work; the template's coverage was thin from the start (`00-audit.md` §8: 12 unit specs, 0 integration, 1 e2e) and every content module built since inherited that same thin-coverage pattern (a handful of handler/mapper specs per module, not full coverage). Closing this gap is a substantial standalone effort, not something to silently attempt — flagged here rather than fixed, pending a decision on whether to lower the threshold to match reality or invest in writing the missing tests before go-live.
- Backups configured for the Postgres and MinIO volumes — not yet done.
- Reverse proxy (Caddy, chosen for automatic TLS) + production `docker-compose` wiring for the real deploy target (`blog.2vault.site`, a test domain ahead of a more permanent one) — in progress.

**Definition of done:** production stack reachable on the real domain, real content populated, a manual bot-like test against comment submission (skip the captcha) is rejected, backups verified restorable.
